CRC16,CRC32,MD5,SHA1,SHA256,这些是常见的数据校验和哈希算法，用于验证数据的完整性一致性以及身份验证等

CRC16/32

原理：循环冗余校验，利用多项式计算校验值
特点：非加密哈希，设计用以检测数据传输或存储中意外错误
CRC16—输出16位（2字节），CRC—输出32位（4字节）
计算速度快，无法防止恶意篡改
用途：
网络数据校验
存储介质
串口通信

MD5

原理：消息摘要算法，输出128（16字节）哈希值
特点：
加密哈希值（但已经被攻破），曾经用于数据完整性，密码存储等
抗碰撞性已不满足安全要求，可在较短时间内找到碰撞
用途：
文件完整性校验
软件发布验证
旧系统或非安全场景的签名

SHA1

原理：安全哈希算法 输出160位（20字节）
特点：
比MD5安全强度高，但在2005年被证明有碰撞可能，在2017年有碰撞案例
目前不推荐使用于安全证书或数字签名
作用：
git提交哈希
某些旧版ssl/tls证书签名
备份校验等不要求防攻击的场景

SHA256

原理：SHA-2家族成员，输出256位（32）哈希值
特点：
广泛认为是安全的，抗碰撞性较强。
计算速度比MD5和SHA1慢，但安全性较高
用途：
TLS证书，数字签名。
文件完整性验证。
密码哈希。
区块链

使用场景分类：
错误检测 CRC16/32
数据完整性校验 MD5/SHA1 SHA256
密码学用途 MD5/SHA1 SHA256
安全性敏感 SHA256 SHA1

what

什么是协程

1️⃣ 核心结构体
① 协程对象 stCoRoutine_t
···c/c++
struct stCoRoutine_t {
void stack_mem; // 栈指针
size_t stack_size; // 栈大小
void stack_sp; // 当前栈指针（切出时保存）
int cStart; // 是否已启动
int cEnd; // 是否已结束
void arg; // 协程参数
pfn_co_routine_t pfn; // 协程入口函数
stCoRoutine_t pCallFrom; // 调用者协程
};
···

重点理解：

保存协程上下文、栈信息和状态
切换协程就是保存/恢复这个结构体里的内容

② 协程调度器环境 stCoRoutineEnv_t
···
struct stCoRoutineEnv_t {
stCoRoutine_t pCallStack[MAX_COROUTINE_DEPTH]; // 当前协程栈链
stCoRoutine_t pending_co; // 待运行协程
// 事件驱动相关 epoll, timer 等
};
···
重点理解：

每个线程一个调度器
维护协程状态、调度队列、事件循环
③ IO/事件结构 stCoEpoll_t
保存 epoll fd
保存协程对应的 IO 事件
核心功能：挂起协程等待 IO → IO 就绪恢复协程

int co_create(stCoRoutine_t *ppco, pfn_co_routine_t pfn, void arg);

ppco：返回创建好的协程对象指针
pfn：协程执行函数
arg：传入协程的参数

2️⃣ 核心实现流程
步骤 1：获取当前线程调度器环境

stCoRoutineEnv_t *env = co_get_curr_thread_env();

步骤 2：分配协程对象
stCoRoutine_t co = (stCoRoutine_t)malloc(sizeof(stCoRoutine_t));
memset(co, 0, sizeof(stCoRoutine_t));
初始化为 0
还没有分配栈

步骤 3：分配协程栈

ntyco 支持 独立栈 / 共享栈：

co->stack_mem = malloc(STACK_SIZE); // 独立栈
co->stack_size = STACK_SIZE;
co->stack_sp = co->stack_mem + STACK_SIZE; // 栈顶
对于共享栈，需要从 stShareStack_t 获取一块栈内存
栈大小可以默认，也可以在 API 中指定

步骤 4：初始化协程上下文

使用 ucontext API 或汇编：

getcontext(&co->ctx); // 初始化上下文
co->ctx.uc_stack.ss_sp = co->stack_mem; // 栈起始位置
co->ctx.uc_stack.ss_size = co->stack_size;
co->ctx.uc_link = NULL; // 协程结束后返回
makecontext(&co->ctx, (void(*)())co_entry_func, 1, co);
co_entry_func 是库内部封装函数，用于：
调用用户传入的 pfn(co, arg)
协程结束后标记状态为 DEAD
自动切回调用者协程

步骤 5：设置协程状态和函数参数
co->pfn = pfn; // 用户协程入口
co->arg = arg; // 用户参数
co->cStart = 0; // 未启动
co->cEnd = 0; // 未结束
状态在第一次 co_resume 时变为 RUNNING
pCallFrom 指向调用协程，方便 co_yield 切回

步骤 6：返回协程对象
*ppco = co; // 返回给调用者
return 0; // 成功
协程现在已创建，但 尚未运行
需要通过 co_resume(co) 才会进入调度器执行

void co_resume(stCoRoutine_t *co);

核心源码逻辑（精简版）

ntyco 里的逻辑大概是：

void co_resume(stCoRoutine_t co)
{
stCoRoutineEnv_t env = co->env;

stCoRoutine_t *curr = env->pCallStack[env->iCallStackSize - 1];

// 记录调用者
co->pCallFrom = curr;

// 放入调用栈
env->pCallStack[env->iCallStackSize++] = co;

// 上下文切换
co_swap(curr, co);

}

这个函数真正的核心其实是：

co_swap(curr, co);

4️⃣ co_resume 第一步：获取当前协程
stCoRoutine_t *curr =
env->pCallStack[env->iCallStackSize - 1];

5️⃣ 第二步：记录调用者
co->pCallFrom = curr;

6️⃣ 第三步：压入调用栈
env->pCallStack[env->iCallStackSize++] = co;

7️⃣ 第四步：真正上下文切换
co_swap(curr, co);

what

什么是reactor？

Reactor 模式简介

Reactor 模式是一种 事件驱动架构模式，用于高并发 I/O 处理。
核心思想：事件检测与事件处理分离。

系统由两部分组成：
Reactor（事件分发器）：等待事件发生，分发给合适的处理器。
Handlers（事件处理器 / 回调）：实际处理事件逻辑（如 accept、recv、send）。

工作原理
注册事件：
将监听 socket 或客户端 socket 的可读/可写事件注册到 Reactor（你的代码用 epoll）。
等待事件：
Reactor 阻塞等待事件发生（epoll_wait）。
事件分发：
当事件发生时，Reactor 调用相应的回调函数：
处理事件：
回调函数完成实际 I/O 操作和状态管理。
根据需要修改事件类型（可读/可写），保持非阻塞连续处理。
特点
高并发：单线程也能处理大量连接。
非阻塞：只在事件发生时才处理，CPU 不会浪费在空等待上。
可扩展：每个连接维护独立状态和回调，便于管理。
核心：
事件循环 (epoll_wait)
事件注册/切换 (set_event)
回调函数 (accept_cb, recv_cb, send_cb)

在你的服务器中如何体现
epoll → Reactor（事件分发器）
conn_list 回调指针 → Handler（事件处理器）
event_register + set_event → 注册事件和切换事件类型

main() → 永久事件循环，检测事件并调用回调
状态机（status） → 控制响应流程，实现异步非阻塞

when

使用场景

why

为什么要使用reactor

  1. 高并发处理
    传统阻塞 I/O 每个连接需要一个线程，连接数量多时会消耗大量系统资源。
    Reactor 模式通过 单线程事件循环 + 回调，就能处理成千上万的客户端连接。
    你的服务器就是用 epoll + 回调实现了高并发客户端管理。
  2. 非阻塞异步
    Reactor 模式保证服务器不会在 recv() 或 send() 阻塞。
    事件发生时才处理对应回调，CPU 不会空转等待。
    提高系统吞吐量，降低延迟。
  3. 可维护性和解耦
    事件检测（Reactor）和事件处理（回调）分开。
    每种操作（accept/recv/send）都有独立回调。
    你的 conn_list + 回调机制就是典型的解耦设计，方便扩展功能（比如增加日志、认证、HTTPS）。
  4. 节约线程和资源
    不需要为每个客户端创建线程。
    减少线程上下文切换，节约内存和 CPU。
    Reactor + epoll 是 Linux 高并发网络编程的经典组合。

how

怎么使用

场景：异步文件/网络 I/O 服务

假设你要实现一个 服务器，既要处理客户端请求，也要读取磁盘文件（比如返回大文件或日志），希望 I/O 都非阻塞。

1️⃣ 初始化监听 socket
···c/c++
TCP 监听 socket，端口 3000：
int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(listen_fd, …);
listen(listen_fd, SOMAXCONN);
set_event(listen_fd, EPOLLIN, 1); // 注册可读事件
注册到 Reactor（epoll），等待客户端连接。
2️⃣ 回调函数设计
accept_cb
接收新客户端
初始化连接上下文
注册客户端 socket 可读事件，绑定 recv_cb
recv_cb
接收请求，例如客户端要求下载某个文件
不直接阻塞读取文件，而是：
打开文件描述符
将文件 fd 注册到 epoll 可读事件（或使用 O_NONBLOCK）
将文件内容读取逻辑交给 send_cb 处理
send_cb
发送缓冲区数据给客户端
如果文件还没读完：
异步读取下一块数据到缓冲区
继续注册 EPOLLOUT
文件读取完成 → 关闭文件 fd → 切回可读事件
3️⃣ 异步文件 I/O 技巧
Linux 提供 非阻塞文件 I/O：
int fd = open(“largefile.dat”, O_RDONLY | O_NONBLOCK);
使用 sendfile() 或 read() + send() 结合状态机发送数据
通过 Reactor 控制文件读取和网络发送：
status = 0 → 准备头部
status = 1 → 读取文件块
status = 2 → 发送完成
4️⃣ 事件循环
struct epoll_event events[1024];
while(1) {
int nready = epoll_wait(epfd, events, 1024, -1);
for(int i=0; i<nready; i++) {
int fd = events[i].data.fd;
if(events[i].events & EPOLLIN)
conn_list[fd].r_action.recv_callback(fd);
if(events[i].events & EPOLLOUT)
conn_list[fd].send_callback(fd);
}
}

场景：即时消息推送系统

假设你要实现一个 多人聊天室服务器，需要同时管理上千个长连接客户端，并实时转发消息。

1️⃣ 初始化服务器
创建监听 TCP socket，并绑定端口（如 5000）。
注册到 epoll 监听 可读事件（EPOLLIN）。
初次连接由 accept_cb 接受。
int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(listen_fd, …); // 绑定 IP/端口
listen(listen_fd, SOMAXCONN);
set_event(listen_fd, EPOLLIN, 1); // 监听可读事件
2️⃣ 客户端上下文
每个客户端连接维护独立上下文：
struct client_conn {
int fd;
char rbuffer[1024];
char wbuffer[1024];
int rlength, wlength;
int status;
RCALLBACK send_callback;
union { RCALLBACK recv_callback; RCALLBACK accept_callback; } r_action;

status 用于区分：
0 → 等待消息
1 → 待发送消息
2 → 已发送完成
3️⃣ 回调函数设计
accept_cb
接收新客户端连接
初始化客户端上下文
注册客户端 socket 可读事件，绑定 recv_cb
recv_cb
接收客户端发送的消息
将消息广播到其他客户端
更新其他客户端的 wbuffer 和状态为可写（EPOLLOUT）
修改事件类型为可写
send_cb
发送缓冲区消息到客户端
发送完成后切换回可读事件（EPOLLIN）

Reactor 主循环：
struct epoll_event events[1024];
while(1) {
int nready = epoll_wait(epfd, events, 1024, -1);
for(int i=0; i 0 && i != sender_fd) {
memcpy(client_list[i].wbuffer, msg, len);

当某个客户端发送消息时，Reactor 模式保证 异步广播，不会阻塞其他客户端。

场景：多端口 TCP 服务

假设你要实现一个服务器，监听 多个端口，不同端口对应不同服务逻辑（例如 2000 端口处理 HTTP 请求，2001 端口处理 WebSocket，2002 端口处理自定义 TCP 协议）。

1️⃣ 初始化多个监听 socket
unsigned short ports[] = {2000, 2001, 2002};
int num_ports = sizeof(ports)/sizeof(ports[0]);

for(int i=0; i<num_ports; i++) {
int sockfd = socket(AF_INET, SOCK_STREAM, 0);

struct sockaddr_in addr;
addr.sin_family = AF_INET;
addr.sin_addr.s_addr = htonl(INADDR_ANY);
addr.sin_port = htons(ports[i]);

bind(sockfd, (struct sockaddr*)&addr, sizeof(addr));
listen(sockfd, SOMAXCONN);

conn_list[sockfd].fd = sockfd;
conn_list[sockfd].r_action.accept_callback = accept_cb;
set_event(sockfd, EPOLLIN, 1); // 注册可读事件

}

每个端口都会注册到 epoll，并且监听可读事件，由 accept_cb 处理新连接。

2️⃣ 回调函数设计
accept_cb
接受来自任意端口的新连接。
根据端口选择不同业务逻辑：
int accept_cb(int fd) {
int clientfd = accept(fd, …);

// 根据监听端口选择回调
if (fd == http_port_fd) {
    conn_list[clientfd].r_action.recv_callback = http_recv_cb;
} else if (fd == ws_port_fd) {
    conn_list[clientfd].r_action.recv_callback = ws_recv_cb;
} else {
    conn_list[clientfd].r_action.recv_callback = custom_recv_cb;
}

set_event(clientfd, EPOLLIN, 1);

}
recv_cb / send_cb
每个端口的客户端可以有独立处理逻辑。
发送和接收都通过状态机控制。
3️⃣ 事件循环
Reactor 主循环保持不变：
struct epoll_event events[1024];
while(1) {
int nready = epoll_wait(epfd, events, 1024, -1);
for(int i=0; i<nready; i++) {
int fd = events[i].data.fd;
if(events[i].events & EPOLLIN)
conn_list[fd].r_action.recv_callback(fd);
if(events[i].events & EPOLLOUT)
conn_list[fd].send_callback(fd);

epoll的边缘触发与水平触发

边缘触发：来数据的时候触发
水平触发：有数据的时候触发

边缘触发：适合非阻塞io，且需要搭配while让数据读完，适合数据大小不确定的情况
水平触发：适合阻塞io，不需要while，适合数据大小一致的情况

epoll相比于select的优势

1.监控数量无上限 vs 有硬性限制

select：默认最多只能监控 1024 个文件描述符（FD_SETSIZE），虽然有办法修改，但需要重新编译内核，很不方便。
epoll：理论上无上限，可监控的文件描述符数量只受操作系统最大打开文件数（ulimit -n）的限制

2.效率差异巨大，复杂度 O(1) vs O(n)
这是最核心的性能区别。
select：每次调用都需要线性扫描全部 fd 集合，时间复杂度为 O(n)
epoll：通过内核回调机制，只返回真正就绪的 fd。程序直接处理这些就绪的 fd，无需扫描全集。时间复杂度为 O(1)，海量连接下依然高效。

3.内存拷贝方式不同
select：每次调用 select() 都需要将整个 fd_set 从用户态拷贝到内核态，连接很多时，内存拷贝开销巨大。
epoll：通过 epoll_ctl() 添加 fd 时只拷贝一次并存入内核红黑树，后续 epoll_wait() 无需再拷贝，大大减少了内存复制的开销。

4.触发模式灵活
select：仅支持水平触发（LT），只要缓冲区有数据，就会一直通知。
epoll：支持边缘触发（ET），只在文件描述符状态发生变化时（如无数据→有数据）才通知一次。这迫使程序一次性处理完所有数据，结合非阻塞 I/O，能显著减少 epoll_wait 的调用次数，进一步提升性能。

poll对select的优势

1.没有最大文件描述符数量限制 (FD_SETSIZE)
select：使用固定大小的 fd_set 位图，默认最多只能监控 1024 个文件描述符。虽然可以修改宏重新编译内核，但非常麻烦且容易出错。
poll：基于 数组 (struct pollfd *fds) 管理，理论上只受系统最大打开文件数 (ulimit -n) 的限制。

2.事件描述更清晰，解决了“输入输出混杂”问题
select：使用 fd_set 位图时，传入的集合会被内核修改，只保留就绪的 fd。这意味着每次调用 select 前都必须重新添加所有关心的 fd，既繁琐又容易出错。
poll：将事件分为 events（输入，表示程序关心的事件）和 revents（输出，表示实际发生的事件）。内核不会修改 events，每次调用前只需设置一次，调用后检查 revents 即可。代码逻辑更清晰。

3.事件类型更丰富
select：只提供相对有限的几类事件：read、write、except。
poll：支持更精细的事件，比如：

POLLRDHUP：对端关闭连接，对于检测客户端断开非常有用。
POLLPRI：紧急数据带外数据。

POLLERR、POLLHUP、POLLNVAL 等错误状态，可以直接通过 revents 获取，无需额外调用。

4.管理大量描述符时，性能略优
虽然两者时间复杂度都是 O(n)，但 poll 在内核中的实现通常比 select 略有效率。select 需要复制三个位图并扫描整个 fd_set 范围（从 0 到 max_fd），而 poll 只需复制用户态的 pollfd 数组，只遍历数组中有意义的部分，减少了遍历无效描述符的开销。

poll，select对epoll的优势

1.无与伦比的可移植性

2.epoll 并非在所有场景下都是最优解。当满足以下条件时，select/poll 的性能与 epoll 几乎无差别，甚至因为实现简单而略占优势：

监控的文件描述符数量很少：
例如只监控 几十个 以内的 fd。此时，select/poll 线性扫描的开销（O(n)）极小，epoll 建立红黑树和回调机制的复杂开销反而显得“杀鸡用牛刀”。

所有监控的 fd 都非常活跃：
例如一个 FTP 服务器，所有连接都在疯狂传输数据。此时，select/poll 每次调用扫描后，发现几乎所有 fd 都就绪了。epoll 的优势在于“只返回活跃的”，但如果所有 fd 都活跃，epoll 就失去了这个优势，反而还要负担红黑树管理和回调的额外开销。在这种场景下，select/poll 的性能和 epoll 几乎持平，甚至可能更好。

总结

select，poll，epoll解决的都是io事件触发
一个io的生命周期由无数个事件组成

server端，事件—>返回不同的回调函数

什么是reactor：
由以前的io管理，改为了事件管理
